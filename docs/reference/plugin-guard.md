One of the [OpenCode plugins](opencode-plugins.md). [Environment variables](environment.md) points here for its switches.

**What it does.** Enforces the safety rules at the tool boundary — before a tool call runs, not after. High-confidence patterns only, so legitimate work is not caught.

- **Blocks** writes to private-key and credential files and writes whose content carries a credential (*Sealed Secrets*; an install built `--no-secrets-gate` carries `Secrets gate: off` in its `AGENT.md`, read once at load, and both stop blocking), catastrophic shell commands such as deleting the filesystem root and every command that would really lose data — a protected branch deleted or force-pushed, an unpushed unmerged branch deleted, a protected branch force-moved off commits nothing else holds, unpushed commits abandoned by `reset --hard`, uncommitted work discarded other than by `reset --hard`, a stash dropped, files git cannot restore removed — judged against the repository's state, the same decisions the Claude/Bob hook makes (*Deletion Is Deliberate*; `reflog expire` and `gc --prune` are left to the `permission.bash` ask; an install built `--no-deletion-gate` carries `Deletion gate: off` in its `AGENT.md`, which the plugin reads once at load and then stops blocking real loss — catastrophic commands still block), a recursive scan rooted at a whole filesystem such as `find /` (*Commands Must Return* — search a specific directory instead), and any change — write, move, rename, delete — under a wiki folder declared `protected` in `geneseed-wiki.jsonc`, and writes to a check listed in the project's `.geneseed/protected-checks.txt` (*External Gate* — see [Hooks](../concepts/hooks.md)). The guard also refuses a write to the other hosts' Geneseed-only files (their `excludes.json`, `AGENT.md` and manifests) and to the shared exclude list in `~/.config/geneseed/`; OpenCode's own config and the shared hook settings get `permission.edit` "ask" keys in `opencode.json` instead, so you see OpenCode's prompt. A shell write is read as well: the targets of `>`, `>>`, `tee`, `sed -i`, `cp`, `mv`, `rm` and the PowerShell writers listed under **Shell is not a boundary** get the same path checks, by path only. `permission.edit` never sees a shell command and this hook has no ask tier, so a shell write to those "ask" files is refused too.
- **Reminds, once:** it refuses the first write of a session in an application repo (a git root holding a build manifest) whose root `AGENTS.md` has no `## Ownership` section, so the agent proposes the [ownership](../concepts/ownership.md) setup first. This is a reminder, not a gate: the next write passes whatever the agent did, and a sub-agent's session never triggers it. Off per repo with `mode: off` in that section, or for one developer with a personal `Setup: declined <YYYY-MM-DD>` line in `.geneseed/ownership.md`; an install built `--no-ownership-gate` carries `Ownership gate: off` in its `AGENT.md`, read once at load.
- **Stands down for `External gate: off`** in `AGENT.md` (an install built `--no-external-gate`, read once at load): it stops refusing protected checks and gate configuration on the write and shell paths, and OpenCode 2's `evaluate` stops asking over those files. The `permission.edit` keys in `opencode.json` are host configuration: they stay, and OpenCode keeps asking before an edit tool writes those files. Every other block stays, the NTFS stream refusal included.
- **Stands down for an excluded rule** read off `AGENT.md`'s `Active packs:` and `Excluded rules:` lines at load, the state the hooks get as flags: with *Persist Insight* (process 1) or its pack off it refuses no rule-store write, by any tool or shell, and OpenCode 2's `evaluate` stops asking over those files; with *Commands Must Return* (ops 2) or its pack off it stops refusing a root scan. The emit also drops the `permission.edit` keys on the rule files. The change report still lists a rule-file change. Every other block stays.
- **Warns** (logged, allowed) on `.env` writes.
- **Leaves to OpenCode's own prompt** a write to `user-rules.md` or `user-rules.draft.md`, because a standing rule is your call (*Persist Insight*). Memory is not gated: the agent writes `MEMORY.md` and the facts in a memory store on its own, and you see them afterwards in the web console. The emit writes `permission.edit` "ask" keys for them, so OpenCode asks you inside its edit, write and patch tools. On OpenCode 2 the `permission.hook("evaluate")` hook asks as well, even over an earlier "always". On OpenCode 1 the guard reads the merged config and refuses the write when it would not make the host ask. The check reads the file a write lands on: `..` and `//` folded, links followed and, on Windows, a stream or trailing dots and spaces taken off, so a memory file linked to `user-rules.md` is still a rule write. A hard link has no target to follow, so a write to a second name of a known rule file gets the same prompt: the gate compares the file's device and inode with the `user-rules.md` and `user-rules.draft.md` of the install, the shared tier, the project at the session's git root and the homes `$GENESEED_HARNESS` and `$GENESEED_MEMORY` name. Any other hard-linked file, a pnpm store's for example, is ordinary work. A file-tool write the host cannot prompt for is refused, so a re-issue changes nothing: any tool other than OpenCode's own edit tools and a named read set (the path-like arguments it carries are read), a config or an agent's own rules with no ask for that path, and on OpenCode 1 any write after you answered "always" to an edit.

**Shell is not a boundary.** The guard reads only the parsed forms: a redirect, `tee`, `cp`, `mv`, `rm` and `sed -i`, and in PowerShell `Add-Content`, `Set-Content`, `Out-File`, `Clear-Content`, `Remove-Item`, `Copy-Item`, `Move-Item`, `New-Item` and `Rename-Item`, with the aliases `ac`, `sc`, `del`, `copy`, `move`, `ni` and `ren`. A cmdlet name matches in any case, and a pipe into one counts (`| Out-File x`). The reader takes `-Path`, `-LiteralPath`, `-FilePath`, `-Destination` and a first positional path, quoted or bare. A path may open with `~`, `$HOME`, `${HOME}`, `$env:HOME` or `$env:USERPROFILE`. One that lands in a rule store gets OpenCode's prompt on OpenCode 2, through `evaluate` on the shell tool's own permission check, and is refused on OpenCode 1, which cannot ask. Everything else in a command goes unread: `bash -c`, `pwsh -c`, an interpreter, `dd`, `curl -o`, `[IO.File]::WriteAllText`, any other variable. The reader names real write targets; it is no text scan, so `Get-Content MEMORY.md` and a commit message that names the file stay free. The host's own command permission (`permission.bash`) is the backstop for those, and the [change report](../concepts/hooks.md#the-change-report) tells you afterwards. It detects; it does not prevent.

It ships whole on every install, whatever [doctrine packs](../concepts/rules.md) you chose. On Claude Code the same checks are hooks, which can *ask* you instead of refusing; Bob has no ask tier, so its hook blocks or warns; OpenCode's tool hook has no ask tier either, so an ask there comes from `permission.edit`.

**"Always" on OpenCode 1.** Its edit tools offer "always" with the pattern `*`, which approves every edit until OpenCode restarts. The host would then ask nothing, so the guard refuses rule writes from that answer on, and writes to the files `permission.edit` asks about, such as `opencode.json` and the guard itself. Restart OpenCode to get the prompt back. The guard sees only an answer it heard: one given in this OpenCode instance after the plugin loaded. OpenCode 2 asks whatever you answered before.

**Agents on OpenCode 1.** The tool hook does not name the agent, so the guard reads every agent's rules through `client.app.agents()` and passes a write only if none of them allows it outright. One agent with its own `edit: allow` therefore refuses these writes for all of them.

Protected wiki folders are enforced only here — on the other hosts they are an instruction.

There is no DYNAMIC loop/* exemption on OpenCode — OpenCode 1 declares a `permission.ask` plugin hook but never calls it, so this guard cannot let a loop's own commit through the way the Claude/Bob git-gate's `loopExempt` does. A loop's commit on OpenCode still gets the static `permission.bash` ask, every time. A push to a `loop/*` branch does not: pushing a loop branch is not pushing `main`/`master`, so [`js/hosts/settings.mjs`](../../js/README.md) wires a static `allow` for the exact refspec shapes the loop engine pushes (`git push [-u] <remote> HEAD:loop/<slug>`, and the `refs/heads/` spelling) — never `main`/`master`, and a force push, a `+refspec`, or a `--delete`/bare-`:` push to a `loop/*` branch still asks, through the push chain's own tiers or the blanket `git push*` ask.

**When it runs.** Before every tool call (`tool.execute.before`).

**What you see.**
- **A refused call** reads `[geneseed-guard] blocked: Tell the user this, word for word: <what changes>`, then why it was refused, what you can do yourself, and a last line for the agent. Nothing can be allowed here, so you depend on the model to relay this text. That is best effort. The [change report](../concepts/hooks.md#the-change-report) reaches you directly. OpenCode 2 refuses by renaming the call and prints `No tool named "<name>"`, so there the name opens `BLOCKED, not a missing tool: `, and the model receives the whole text (seen on 2.2.6). The one exception is the ownership reminder above: it is an instruction to the agent, not text for you, so it keeps its own words.
- **A prompt** comes from OpenCode, and its dialog shows no plugin text. So for its two asks, a rule write that reaches a host prompt and a gate configuration file, the guard posts the reason just before the dialog, inside a delimiter:

  ```text
  ──── Geneseed · about the next permission request ────
  This edit changes user-rules.md, your standing rules, which the agent obeys in every session.
  Safe choice: Deny, unless you asked for this rule. (Persist Insight)
  It asks because what becomes a rule is your decision.
  If you allow it, the text binds every later session until you remove it.
  ──── The dialog below is for this change ────
  ```

  OpenCode 2 shows it as a message in the session. The model gets one short line instead of this text. OpenCode 1 shows it as a toast, which can expire while the dialog is still open. `opencode run` and `mini` do not show the OpenCode 2 message. An unattended OpenCode 2 session posts the note and then denies the call. A failed post changes nothing: the prompt still asks. The note shows no line count.

[What a prompt says](../concepts/hooks.md#what-a-prompt-says) lists what this text can and cannot tell you.

The guard's reasons are the same words as the hooks'. The reason never names the switches below: the agent reads it, and a switch named there reads as leave to get round the block. The *Persist Insight* reason tells the agent to ask you and that a re-issue changes nothing — never to write the file another way (through a shell command, say). Warnings go to OpenCode's own log on OpenCode 1 (service `geneseed-guard`) and to stderr on OpenCode 2.

**Switches.**
- `GENESEED_GUARD=warn` — log every block, allow the call.
- `GENESEED_GUARD=off` — disable the guard.
